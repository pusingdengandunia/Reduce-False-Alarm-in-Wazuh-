# 2. The AI Model

Specification item 5 requires that the model be developed independently and that no
third-party AI API be used. Everything described here runs on our own Manager VM. There is no
outbound call to any model provider at inference time; the only network hop is
`127.0.0.1:5000`.

## 2.1 Problem statement

Binary classification over Wazuh alerts.

- `label = 0` — false positive. Benign activity that tripped a rule. Analyst should not be paged.
- `label = 1` — true positive. Activity that warrants analyst attention.

The model outputs a probability for class 1. Alerts scoring below a threshold are marked
`is_false_positive: true` and recommended for suppression.

## 2.2 Defining "false alarm"

Specification item 4 asks us to define false-alarm criteria independently from Wazuh data. We
exported 738 real alerts from the running deployment and labeled them against these rules:

| Criterion | Label | Reasoning |
|---|---|---|
| Routine system housekeeping (log rotation, service restart on a schedule) | 0 | No adversary involvement possible |
| Expected administrative action from a known source | 0 | Authorized activity |
| Health-check and monitoring traffic against nginx | 0 | Generated by our own tooling |
| Informational rules at level 3 with no security semantics | 0 | Noise by definition |
| Authentication failure against a non-existent user | 1 | Username enumeration |
| Web server 4xx bursts consistent with probing | 1 | Reconnaissance |
| Modification of `root`'s crontab | 1 | Classic persistence technique |
| Unexpected connection resets from external sources | 1 | Scanning artifact |

The resulting distribution in `data/wazuh_real_flat.csv`:

```
label
0    499
1    239
```

That is a 2.1:1 imbalance — mild enough that class weighting alone is sufficient and
oversampling is unnecessary.

## 2.3 Feature set

Seven features, in the exact order the serving code expects. The order is pinned in
`ai-classifier/model_config.json` and cross-checked against the estimator's
`feature_names_in_` attribute.

| # | Feature | Type | Source field |
|---|---|---|---|
| 0 | `rule.level` | numeric | `rule.level` |
| 1 | `data.alert.severity` | numeric | `data.alert.severity`, falling back to `rule.level` |
| 2 | `hour` | numeric | hour of day parsed from `timestamp` |
| 3 | `day_of_week` | numeric | 0 = Monday … 6 = Sunday |
| 4 | `is_weekend` | binary | 1 when `day_of_week` is 5 or 6 |
| 5 | `rule.id` | label-encoded | `rule.id` |
| 6 | `data.alert.signature_id` | label-encoded | `data.alert.signature_id` |

The temporal features encode the intuition that maintenance noise clusters in scheduled
windows while opportunistic attacks do not respect business hours.

> **Defect.** Features 5 and 6 are the direct cause of the label leakage documented in
> [05-results-analysis.md](05-results-analysis.md). They are listed here because they are what
> the deployed artifacts actually use, not because they are correct.

## 2.4 Algorithm

`RandomForestClassifier` inside a scikit-learn `Pipeline`, selected over gradient boosting for
three reasons: it handles label-encoded categorical features without requiring one-hot
expansion, it gives calibrated-enough `predict_proba` output for thresholding, and it trains in
seconds on a dataset this size, which matters when iterating on a free-tier VM.

Final hyperparameters:

```python
rf_params = {
    'n_estimators':     300,
    'max_depth':        15,
    'min_samples_split': 20,
    'min_samples_leaf':  10,
    'max_features':     'sqrt',
    'max_samples':       0.8,
    'class_weight':     'balanced',
    'random_state':      42,
    'n_jobs':           -1,
}
```

`min_samples_leaf=10` and `max_depth=15` were chosen as regularization against overfitting on
a small dataset. `class_weight='balanced'` handles the 2.1:1 imbalance directly.

SMOTE was evaluated (`imblearn.pipeline.Pipeline` with `SMOTE`) and dropped. At this imbalance
ratio, synthetic minority oversampling added variance without improving held-out scores, and
class weighting is the simpler mechanism.

## 2.5 Training pipeline

Implemented in `notebooks/labellingFalsePositive.ipynb`.

1. **Dataset assembly.** The 738 real labeled alerts are augmented with synthetic alerts
   generated from a rule catalog (`tp_rules` for attacks, plus benign patterns), producing
   2000 rows at 1396 / 604.
2. **Temporal expansion.** `timestamp` is parsed and expanded into `hour`, `day_of_week`,
   `is_weekend`; the raw timestamp, `agent.name`, and `rule.description` are dropped.
3. **Categorical encoding.** Two `LabelEncoder` instances are fitted and serialized:
   - `le_rule_id.pkl` — 79 classes
   - `le_signature_id.pkl` — 84 classes
4. **Hyperparameter search.** `GridSearchCV` over `max_depth`, `min_samples_leaf`,
   `class_weight`, and `n_estimators`, with `StratifiedKFold(n_splits=5, shuffle=True,
   random_state=42)`.
5. **Serialization.** `joblib.dump` of the fitted pipeline plus both encoders.

> **Defect.** The grid search scored every candidate as `nan`, so it selected no parameters
> on merit. Cause and fix in [04-benchmarks.md](04-benchmarks.md#43-the-nan-scorer-defect).

## 2.6 Serving

`ai-classifier/app.py`, a Flask application run by systemd as a persistent service.

### Endpoints

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/health` | Liveness probe. Returns `{"status": "ok"}` |
| `POST` | `/analyze` | Scores one alert. Returns the verdict object |

### Response schema

```json
{
  "alert_id":          "1789967652.435830",
  "is_false_positive": true,
  "confidence":        0.0,
  "action":            "suppress"
}
```

| Field | Meaning |
|---|---|
| `alert_id` | Wazuh's `id`, echoed so the verdict can be joined back to the alert |
| `is_false_positive` | `true` when `predict_proba < threshold` |
| `confidence` | Probability of class 1 (true positive), rounded to 4 places |
| `action` | `suppress` when `is_false_positive`, otherwise `escalate` |

Note that `confidence` is the probability of the alert being a **true positive**, not the
model's confidence in its own answer. A value of `0.0` alongside `"action": "suppress"` means
the model is certain the alert is benign.

### Decision threshold

```json
{"threshold": 0.491}
```

Loaded at startup from `model_config.json`. Keeping it in configuration rather than code lets
an analyst retune the precision/recall trade-off without redeploying the service — lower the
threshold to suppress more aggressively, raise it to escalate more.

### Robustness

Every parsing step in `extract_features` is wrapped in `try/except` with a defined fallback:

- Unparseable `timestamp` → `hour`, `day_of_week`, `is_weekend` all set to 0.
- `rule.id` unseen by the encoder → encoded as 0.
- `data.alert.signature_id` absent or unseen → encoded as 0.
- Non-numeric `data.alert.severity` → falls back to `rule.level`.

This guarantees the service never returns 500 on a malformed alert, which matters because
`wazuh-integratord` treats a non-zero exit from an integration as an error and logs it on every
single alert. The cost of that robustness is analyzed in
[05-results-analysis.md](05-results-analysis.md#gap-2-silent-encoder-fallback).

### Deployment

`/etc/systemd/system/ai-classifier.service`:

```ini
[Unit]
Description=Wazuh AI Classifier
After=network.target

[Service]
ExecStart=/home/azureuser/myenv/bin/python3 /opt/ai-classifier/app.py
Restart=always
User=root

[Install]
WantedBy=multi-user.target
```

`Restart=always` keeps the service up across crashes. `User=root` is stronger than necessary —
the service needs only read access to `/opt/ai-classifier` and the ability to bind a loopback
port above 1024. Running it as a dedicated unprivileged user is a recommended hardening step.
